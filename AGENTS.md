# nemar-metadata

Consumer of the shared `hed-metadata-toolkit` package, scoped to the [nemarDatasets](https://github.com/nemarDatasets) GitHub organization: it catalogues those dataset repositories and builds per-dataset summaries for HED (Hierarchical Event Descriptors) annotation.

**This repo is configuration and data.** All pipeline logic lives in the toolkit. There is no code here at all - no `src/`, no `tests/`, and `pyproject.toml` declares `packages = []`; it exists to pin the dependencies. If NEMAR needs behaviour the toolkit lacks, the fix is a configuration option in the toolkit (like `--prefix` or `--include-subdir`), never a fork of toolkit code into this repo.

## The organization

- Dataset repositories are named `nm******` (native NEMAR) or `on******` (mirrored from the matching `ds******` dataset on [OpenNeuro](https://openneuro.org)).
- Every dataset carries a `.nemar/` subdirectory, mirrored alongside the top-level files via `--include-subdir .nemar`.
- `.nemar/metadata.json` supplies `title` and `links` to the summary and nothing else. Its `modalities` list is not used - the summary's `datatypes` column is derived from the directory tree, and the two can disagree.

## Commands

Test framework: pytest. There is no test suite in this repo (no `tests/` directory); the toolkit's own suite is the gate for pipeline behaviour. If tests ever appear here, they are pytest - plain functions, no `TestCase` classes - and the pytest keys go back into `.vscode/settings.json`.

The `hed-*` commands come from installing the toolkit; they are not files in this repo. Run everything from the repo root: output paths resolve relative to the current directory, and every command loads `.env` from the directory it runs in (`GITHUB_TOKEN`, `HED_CACHE_DIR`; `.env.example` documents both).

**`--org nemarDatasets` is required on every command that talks to GitHub.** There is no default organization; a wrong organization returns 404 per file and leaves empty dataset directories rather than raising. `--prefix` defaults to `nm on`, so it can be omitted here.

The pipeline, in order (each step reads the previous step's output):

| Step | Command | Writes (under `datasets/dataset_summaries/` unless noted) |
| ---- | ------------------------------------------------------------- | ---------------------------------------------------------- |
| 1 | `hed-fetch-repo-list --org nemarDatasets` | `datasets.tsv` |
| 2 | `hed-sync-repo-contents --org nemarDatasets --include-subdir .nemar` | `repo_contents.json` |
| 3 | `hed-sync-local-files --org nemarDatasets` | `datasets/dataset_repos/REPO_NAME/...`, including `.nemar/` |
| 4 (optional) | `hed-sync-repo-file-contents --org nemarDatasets` | `repo_file_contents.json` - one subject per dataset, by design |
| 4b (optional) | `hed-list-event-files --org nemarDatasets` | `event_files.json`, `event_files.tsv` |
| 5 | `hed-extract-summary-info` | `dataset_summary.tsv` |
| 6 | `hed-update-summary`, then `hed-sort-datasets` | updated and sorted summary TSVs |

Steps 5-6 read local data only and take no `--org`. A `*_failures.json` beside each output records what could not be fetched; `--retry-failed` re-attempts those entries, and an entry with `"skip": true` is never retried.

The file formats are the toolkit's contract: its `AGENTS.md` and each writer's module docstring are the definitions. This repo does not redefine them, and a reader here should consult those rather than inferring a schema from a sample file. Two toolkit rules worth repeating because they bite consumers: `repo_file_contents.json` is a deliberate one-subject-per-dataset sample, never event-file coverage (complete discovery is `event_files` in `repo_contents.json` or `hed-list-event-files`); and an entry in `repo_contents.json` lacking `subjects` means rebuild with `hed-sync-repo-contents`, not hand-edit.

The citation steps (`hed-collect-citations` and the rest) are available from the toolkit but unused here so far; they need a `config/citation_skip_list.txt` first, and none exists yet.

## Data

Everything under `datasets/` is gitignored and lives only on the machine that built it. Two kinds of files:

- **Rebuildable** - `datasets.tsv`, `repo_contents.json`, `repo_file_contents.json`, `event_files.*`, `*_failures.json`, and all of `dataset_repos/`. Regenerated by rerunning the pipeline; their loss costs API calls, nothing more.
- **Curated** - `dataset_summary.tsv` once its `contact` and `notes` columns are hand-filled, and any future citation registry (a `cit_######` is permanent; regenerating renumbers everything). These are irreplaceable, and whether they get tracked in git or backed up outside it is an open decision - do not assume either.

## The toolkit dependency

- `pyproject.toml` pins the toolkit **by local path**, and the working setup installs it **editable** on top, so toolkit edits apply here immediately. This is deliberate while the toolkit is under active development, and it is the one sanctioned machine path in a committed file. Switch to a git-tag pin (the toolkit README documents the form) before enabling CI or expecting this repo to install on another machine.
- A toolkit change to a function this repo's pipeline calls, or to a file format it reads, lands here instantly through the editable install - there is no version boundary to hide behind.

## Conventions

- **ASCII only** in prose, comments, and filenames: `-` not em/en dashes, `->` not arrows, `...` not an ellipsis character, straight quotes, `|--` rather than box-drawing characters. The exception is genuine data: dataset titles and author names keep whatever characters they contain.
- **Markdown headers in sentence case** - capitalize the first word only, plus proper nouns and acronyms.
- **Committed files carry no project history** - no dates, no "previously", no session labels. Rationale goes in `.status/decisions.md`.
- **No committed file contains a local path or a drive letter**, with the single exception of the `pyproject.toml` toolkit pin noted above. Machine facts live in `.status/local-environment.md`.
- **Examples use placeholders** (`REPO_NAME`), not real dataset IDs.
- Nothing that ships may reference `.status/`, except the files whose job is to orient a tool - this file, `CLAUDE.md`, `.gitignore`, the files under `.claude/` (`settings.json`, `rules/`), and those under `.github/` (`copilot-instructions.md`, `instructions/`).

## Where the thinking lives

`.status/` is gitignored, so it exists only on the machine that wrote it and never in a fresh clone or worktree.

- `.status/README.md` - the index. Read this first; it lists what is active.
- `.status/decisions.md` - why things are the way they are. Read before proposing structural changes. Append entries; never rewrite one.
- `.status/plans/*.md` - active plans. Check the `Status:` header and the `[ ]` / `[x]` markers before starting work.
- `.status/local-environment.md` - this machine's paths, interpreter, and quirks. Never copy its contents into a committed file.
- IMPORTANT: do not read `.status/archive/` unless a file is named for you. Nothing new is created at the `.status/` root - new material goes in `plans/`, `prompts/`, `notes/`, or `scratch/`.

## Working agreements

- **IMPORTANT: every file written to `.status/` opens with a `For humans:` summary** - three or four sentences at the very top: what this file is and what a person needs to take away. The same applies to a long answer in a session: lead with the conclusion.
- IMPORTANT: never delete or rewrite a file under `.status/` without asking first. Appending is fine.
- IMPORTANT: temporary scripts, experiments, and one-off test files go in `.status/scratch/` - never the repository root.
- Show evidence, not assertions: the command you ran and its actual output. For metadata work, include counts and a sample of records.
- For a change spanning more than three files, write a plan to `.status/plans/` and stop for review before editing.
- When you are guessing about an external API's response, say so.
- Do not commit, push, or create branches unless asked.
